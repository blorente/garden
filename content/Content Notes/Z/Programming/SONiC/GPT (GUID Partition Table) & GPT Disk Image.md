# GPT & GPT Disk Image

https://en.wikipedia.org/wiki/GUID\_Partition\_Table
GUID Partition Table is a standard to store the partition table of a disk.
It's part of the UEFI Standard. [[UEFI]].

The name comes because it uses GUIDs (another name for UUIDs) to identify partitions and partition types.

- the UUIDs for types are just values that the vendor assigned once.
- There is no central registry, so folks can just "claim" types as they will. For instance, here is a standard claiming some types: https://uapi-group.org/specifications/specs/discoverable\_partitions\_specification/
  - Because they're UUIDs, we're not meaningfully claiming any part of the space, and collissions are rare.
- So, if I'm writing a partition table writer, I'll have to look at the vendor for this partition type (e.g. Windows), and see which UUID they want me to write for the type.

How are GPTs read?

- The UEFI firmware reads the partition tables, to look for the EFI partition, and therefore locate where the bootloader is stored.
  - Interestingly, BIOS (previous to UEFI) didn't understand GPTs, and just executed LBA 0 blindly. Fun fun fun.
- The bootloader (usually GRUB) reads the table, to find its own config, where the kernel is, and any bootable drives it can boot to (e.g. dual boot Windows/Linux).
- The Linux kernel reads it again, to create the VFS and mount points to access it.
  - First, the NVMe driver initializes the whole disk.
  - Then the partitions are created by Linux.
    - They are an illusion, created and maintained by the different OSes.
    - (except UEFI also reads partitions, but whatever. We could write a kernel that doesn't have any idea about partitions and just does whatever it pleases).
- The `udev` tool, in initramfs, processes the partitions, instantiates the filesystems, and creates teh `/dev/disk` symlinks.

### A brief detour into Partition tables

- A partition table is a table maintained on disk, _by the OS_ (read; the kernel), which outlines the partitions of that disk.
- GPTs use LBA (Logical Block Addressing):
  - We read the data in sectors, usually of 512 bytes.
  - The sectors 2 to 33 contain the partition table per se, with 128 bytes per entry.

### Linux booting:

https://www.youtube.com/watch?v=EjrAzulPsT4

- GRUB is what loads the initrootfs, or initramfs, or whatever you want to call it.
- Then the kernel mounts it.
- then, the kernel starts process 1, called init. These days, init is systemd almost universally.
- ✅ Why is the ramdisk better than a physical disk?
  - Because the kernel needs drivers to read from disk, but it needs to mount the disk to read the drivers.
  - This initramfs contains kernel modules for uniform drivers, like NVMe, USB, RAID, etc.
    - We can modify it by compiling our own kernel, of course.
      - We can just compile the modules into the kernel
    - Or by shipping our own initramfs without recompiling the kernel.
      - If the kernel is compiled to look for it, it can look for an [[Initial RamDisk (initrd)]] , which must contain a binary called `/linuxrc` which loads the driver modules.
    - Yep. We can ship our own initramfs.
    - https://wiki.debian.org/.internal/challenge.html?original=%2finitramfs#Rebuilding\_the\_initramfs
      - In debian, they build this initramfs with `initramfs-tools`.
  - This is usually bundled as part of the distro.
- ✅ What is mounting a disk?
  - Mounting a disk is the process of tying a device, or a partition in that device, to a file system (sub)tree.
  - We're not going to dive into the implementaiton for now, right? Right?
    - We're really not. But it's mostly an operation where we update the in-memory state of the file system, and then I guess the write machinery is what pipes the actual bytes back and forth.
    - What is the connnection point with the actual disk?
    - Now we're starting to get into the good stuff about partitions.
    - Interestingly, this is represented in linux by what's called a `Superblock Object`: https://docs.kernel.org/filesystems/vfs.html#the-superblock-object
